# Setup plan and approval checklist

## Readiness at Stage 0

The audit host had macOS 26.6.2 (25G83) on arm64, Node 26.13.0, npm 11.20.0, Git 2.54.0, GitHub CLI 2.89.0, and system Chrome 157.0.8103.79. Three.js and Vite were already installed and matched the lock. Playwright Core 1.65.1 existed in an earlier scratch workspace. The repo has no Playwright Test dependency, pinned browser lane, or capture harness. Python 3.14.5, Blender 4.4.0 and FFmpeg 8.1.1 were available and are optional. Hardware WebGL 2 and a usable physical mobile test device are requirements for the designated performance lanes. Browser revisions, acceleration, and device coverage remain open until Stage 2.

## Stage 2 checklist · proposed

- [ ] Approve the dev-only Playwright package, browser download, evidence storage policy, and baseline devices. Pin Node 26.13.0 and npm 11.20.0 for initial reproduction, or review a security patch separately before establishing goldens. Confirm platform support and GPU acceleration.
- [ ] From v0.1 in a separate worktree and branch, record the starting SHA and checksum. Run `npm ci` using the existing lockfile, then `npm run check`. Use a loopback-only Vite server for captures. Audit current advisories and inspect the relevant package lifecycle scripts before enabling them.
- [ ] Review the registry metadata and integrity for `@playwright/test@1.65.1`. With approval, run `npm install --save-dev --save-exact @playwright/test@1.65.1`. Review the lockfile diff, then use the installed CLI to fetch Chromium, e.g. `PLAYWRIGHT_BROWSERS_PATH=0 ./node_modules/.bin/playwright install chromium`. Use the same browser path in capture runs and verify the fetched browser revision against the upstream manifest.
- [ ] Implement the capture and timing harness described in the [protocol](VISUAL-ITERATION-PROTOCOL.md), record v0.1 goldens, and verify reproducibility and the physical-device baseline. Review artifact permissions before publishing. Keep the lockfile and screenshots unchanged until the relevant PR is reviewed. Roll back tooling by reverting the tooling commit on its branch and recreating that worktree from the baseline lock. The browser download is disposable with that worktree.

The local plan requires $0 in fees and uses existing hardware. Confirm disk and bandwidth for browser binaries and evidence before setup. Existing system Chrome or manually captured screenshots can support a labeled exploratory lane while the pinned lane is pending.

## img2threejs · optional Stage 5 evaluation

- The skill release is **2.0.1**, pinned to commit `0c0c49bc168e648dbaf9c8c080474de0b3a941b6`. Its separate npm installer is **0.2.0** with registry integrity `sha512-XZH5ZjuF7C+GJtmLPH0u8PMmh8IjppH3kWO/a1QEOuIYGYH0att31E/2wvfWZEbCsR1GGf97Rbj8q5Sk+wH80A==`. Both declare Apache-2.0. The installer expects Node ≥18 and Git on macOS/Linux, and the core workflow needs Python ≥3.10 and an agent with image and browser access. Core scripts use the Python standard library. Optional adapters/plugins have separate dependencies and are outside this proposal. [Pinned skill](https://github.com/img2threejs/img2threejs/blob/0c0c49bc168e648dbaf9c8c080474de0b3a941b6/SKILL.md)
- The default installer detects supported agent homes, fetches a Git release to `~/.img2threejs/releases/<sha>`, and writes skill symlinks such as `~/.codex/skills/img2threejs`. An unpinned invocation resolves a mutable latest release. The separate plugin harness can create `~/.img2`, add a launcher to a writable PATH directory, and update Claude additional-directory permissions. These are unnecessary for the A/B. The review read installer source and docs without invoking either installer. [Pinned installer](https://github.com/img2threejs/img2threejs/blob/0c0c49bc168e648dbaf9c8c080474de0b3a941b6/bin/img2threejs.mjs) · [Installation docs](https://github.com/img2threejs/img2threejs/blob/0c0c49bc168e648dbaf9c8c080474de0b3a941b6/docs/INSTALL.md)
- Intake creates a detail inventory and structured sculpt spec. Ordered geometry, material, and presentation checkpoints produce comparison sheets. A review decision routes the next pass to continuation, spec correction, code correction, input, or stop. Borrow those ideas for OCTO's ledger immediately. The generated TypeScript factory and standalone spec would require review and integration to match OCTO's existing JS animation, materials, and performance budget. [Pinned architecture](https://github.com/img2threejs/img2threejs/blob/0c0c49bc168e648dbaf9c8c080474de0b3a941b6/docs/ARCHITECTURE.md)
- If approved, review the exact Git object, scripts, external calls and license obligations, then evaluate a pinned checkout in a disposable workspace with isolated agent settings and minimal access. Keep the system-wide installer out of the preferred workflow. Compare one fixed reference crop against the existing procedural pipeline with equal time bounds and the same camera, quality and performance gates. Adoption requires a measurable rubric or turnaround gain. Roll back by discarding the isolated experiment and retaining the scored evidence.

## Approval boundaries

Review the draft foundation first. Approve Stage 2 installation, package/lock changes, browser downloads, and evidence policy before bootstrap. Approve geometry work after the baseline is captured. External asset acquisition, a compositor dependency, img2threejs or other agent settings changes, Blender/GLB, and the WebGPU sandbox each require separate explicit scope approval. Paid services, deployments, and infrastructure are outside this foundation.
